# Spec: Unified Session ID Architecture & Multi-Session Background Concurrency

## Problem Statement

When using Nexus (the HarmonyOS & Flutter remote AI programming client), users face two major limitations:

1. **Session Disconnection on Switch**: When a user switches out of an active chat session to view history, browse workspaces, or start a new conversation, the PC Bridge Server immediately kills the previous AI Agent process (such as OpenCode or Codex CLI). Long-running tasks (like a 5-minute code refactoring or test execution) are prematurely terminated.
2. **Confusing Dual Session IDs**: The codebase maintains two redundant session IDs (`bridgeSessionId` prefixed with `acp-` and the real agent `acpSessionId` such as `ses_...` or UUID). This causes state mismatch, replay bugs, and unnecessary complexity.

Users want to launch long-running AI tasks across multiple sessions simultaneously, leave the sessions to perform other work, observe all active tasks running in real-time with live status badges, and seamlessly switch back to any running session to inspect buffered output.

## Solution

Nexus will implement a **Single Session ID Architecture** combined with **Multi-Session Background Concurrency & Event Buffering**:

- **Unified Session ID**: Eliminate `bridgeSessionId` (`acp-timestamp-...`). Use the AI Agent's real, persistent `sessionId` (`ses_...` or UUID) as the single, canonical session identifier across the entire stack (Flutter App → WebSocket Protocol → Node.js Bridge Server → ACP Agent).
- **Background Process Pool (`activeSessions`)**: Retain running Agent child processes in memory when a user switches away or disconnects. A process is killed only when explicitly deleted by the user or after a 15-minute idle timeout.
- **Incremental Event Buffering (`MessageBuffer`)**: Buffer streaming text chunks and tool calls generated by background sessions in memory. When the user re-enters a running session, the server instantly replays missed events.
- **Real-Time Multi-Task Watcher Sync**: The `session-watcher` monitors disk WAL/mtime and process states every 5 seconds, broadcasting `{ type: "session_status_update", sessions: [{ sessionId, status: "running" }] }` to update green "进行中" status badges on all mobile session cards in real-time.

## User Stories

1. As a mobile developer, I want to start a long-running code refactor task with OpenCode, so that the AI can work autonomously without blocking me.
2. As a mobile developer, I want to exit an in-progress chat session to browse other projects, so that I can manage multiple work items at once.
3. As a mobile developer, I want my background AI task to continue executing on my PC when I navigate away, so that my task is not prematurely killed.
4. As a mobile developer, I want to start a second AI task using Codex while the first task is running, so that I can parallelize my development workflow.
5. As a mobile developer, I want to see a live green "进行中" status badge on every running session in my workspace session list, so that I can monitor progress at a glance.
6. As a mobile developer, I want to tap on a running background session and immediately see all the output generated while I was away, so that I don't lose any conversation history.
7. As a mobile developer, I want my app and server to use a single, unified session ID, so that I never experience session routing mismatches or state corruption.
8. As a mobile developer, I want idle background sessions to automatically shut down after 15 minutes of inactivity, so that my PC's memory and CPU resources are preserved.
9. As a mobile developer, I want background tasks that are actively running to never be killed regardless of duration, so that multi-hour tasks complete successfully.
10. As a mobile developer, I want configuration changes (such as switching models or setting modes) to be scoped strictly to the target session, so that different sessions do not interfere with each other.
11. As a mobile developer, I want real-time session status updates to be debounced and throttled on the server, so that my phone's battery and performance remain unaffected.

## Implementation Decisions

- **Single Session ID Cutover**:
  - The server `SessionState` and WebSocket protocol handlers will use the Agent's real `sessionId` (e.g. `ses_...` or UUID) as the sole primary key in `sessions = Map<string, SessionState>()`.
  - The `bridgeSessionId` generation logic (`acp-${Date.now()}-${randomUUID()}`) will be removed.
  - Client `ChatState` will remove `bridgeSessionId` and maintain `sessionId` as the single canonical field.

- **Process Pool & Background Retention (`activeSessions`)**:
  - In `server/src/session.mts` and handler modules (`start.mts`, `input.mts`, `load-session.mts`), when a WebSocket connection switches sessions or disconnects, the server checks if `sess.turnActive === true` or if the child process is still executing.
  - If active, the process is retained in the `sessions` map instead of being killed via `killSessionProcess()`.
  - An idle timeout (15 minutes) and an LRU eviction cap (max 5 concurrent background ACP processes per bridge) will reclaim idle memory.

- **Turn-Level Message Buffer & Replay**:
  - `SessionState` maintains a sliding array `messageBuffer: Array<{ messageId: string, payload: string, timestamp: number }>`.
  - During background execution, all `agent_event` chunks and `tool_call` updates are appended to `messageBuffer`.
  - On client re-entry (`load_session` / `sync_request`), the server filters `messageBuffer` for messages newer than `lastMessageId` and replays them over WebSocket to the client.

- **Status Watcher & Throttled Broadcast**:
  - `startSessionWatcher()` in `server/src/server.mts` polls `session-watcher` every 5 seconds.
  - Status updates are throttled with a 500ms debounce window and broadcast as `{ type: "session_status_update", sessions: [...] }`.
  - Flutter `SessionTile` renders a green status dot badge and "进行中" text whenever `session.status == 'running'`.

## Testing Decisions

- **Test Seam 1: Unified Session ID RPC Contract**:
  - Test via `server/test-session-watcher.mjs` and Node unit tests.
  - Assert that all WebSocket protocol messages (`session_started`, `agent_event`, `turn_ended`, `session_status_update`) use the exact agent `sessionId` (`ses_...` or UUID) without `acp-` wrappers.
- **Test Seam 2: Background Concurrency & Process Retention**:
  - Spawn two mock ACP sessions (`session-A` and `session-B`).
  - Send `input` to `session-A`, then issue `start` or `load_session` for `session-B`.
  - Assert that `session-A` process remains running, `turnActive` is preserved, and `scanLocalSessionStatuses()` reports both sessions as `running`.
- **Test Seam 3: Message Buffer Replay Integrity**:
  - Execute background turns while client is disconnected.
  - Send `sync_request` with `lastMessageId`.
  - Assert that the client receives the exact sequence of buffered chunks without duplicates or dropped messages.
- **Prior Art**:
  - Built upon `server/test-e2ee-unit.mjs` (in-memory mock transport test) and `server/test-session-watcher.mjs` (scanner & diff engine test).

## Out of Scope

- Multi-device simultaneous write locks (only one mobile client controls a given session at a time).
- Local DB persistence on the mobile client (history resides on the PC server and AI Agent stores).
- Voice input / audio streaming background processing.

## Further Notes

- The single Session ID cutover simplifies state management across ArkTS and Flutter client implementations.
- Background process pool limit (max 5 concurrent sessions) prevents CPU/memory exhaustion on lower-end PC hosts.
